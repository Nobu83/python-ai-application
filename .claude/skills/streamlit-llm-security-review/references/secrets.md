# 観点 1: 秘密情報の漏えい

このアプリの API キーが漏れると、他人が持ち主の課金で API を使える。個人アプリでは
「壊される」より「請求が来る」ほうがずっと現実的な被害なので、ここを最優先で見る。

キーは **保持 → 表示 → 記録 → 保存** の 4 段階すべてに漏えい経路がある。
入り口（キーをどこから読むか）だけ見て安心しないこと。

## 1.1 保持: キーがどこに置かれるか

確認すること:

- キーの取得経路が 1 か所の関数に集約されているか。あちこちで `os.getenv()` を
  呼んでいると、片方だけ対策しても意味がなくなる
- 画面から入力されたキーを**ファイルに書き出していないか**。「次回から入力不要にする」
  という親切心で、平文の JSON や設定ファイルに保存している実装は珍しくない
- キー入力欄が `st.text_input(..., type="password")` になっているか。
  なっていないと、画面共有・肩越し・スクリーンショットでそのまま漏れる
- `st.session_state` に入れたキーが、他の目的で丸ごと表示される経路がないか
  （後述の `st.write(st.session_state)` 問題）

判断:

- 環境変数 / `.env` / プロセス内のモジュール変数に留めるのは妥当。
- キーを引数に取る関数に `@lru_cache` が付いていても、プロセス内に留まる限り
  脆弱性ではない。ただしキーを変更しても古いクライアントが使われ続ける挙動がないかは
  見ておく（機能上の問題として低で挙げる価値がある）。

## 1.2 表示: 画面に出る経路

Streamlit ではデバッグの痕跡がそのまま UI に残りやすい。次を探す。

```python
st.write(st.session_state)        # キー入力欄の値も含めて全部出る
st.json(config)                   # 設定オブジェクトにキーが入っていれば出る
st.code(prompt)                   # プロンプトにキーが混ざっていれば出る
st.write(os.environ)              # 論外
```

`st.session_state` を丸ごと表示する行があれば、それだけで **高**。
キー入力欄のウィジェットキー（例: `api_key_input`）の値が含まれるため、
`type="password"` にしていても画面に平文で出る。

## 1.3 エラーメッセージ（見落としやすい）

**この構成でいちばん見落とされる経路。** 例外の文字列をそのまま UI に流している箇所を探す。

```python
return f"リクエストに失敗しました: {detail}"   # detail は str(exc)
```

SDK や HTTP クライアントの例外は、リクエスト URL・ヘッダ・レスポンスボディを
含むことがある。キーをクエリパラメータで送る API（`?key=AIza...`）では、
これがそのまま画面に出る。

確認手順（推測で書かない）:

1. エラー整形関数を単体で呼び、キーを含む文字列を渡して戻り値を見る
2. 実際に無効なキーで API を叩き、例外の文字列に何が入るかを確認する
   （無効なキーなら流出しても被害がない）

修正案の形:

```python
import re

_SECRET_PATTERN = re.compile(r"(AIza[\w\-]{10,}|sk-[\w\-]{10,}|[A-Za-z0-9_\-]{32,})")

def _redact(text: str) -> str:
    """例外文字列などに含まれる API キーらしき文字列を伏せる。"""
    return _SECRET_PATTERN.sub("***", text)
```

これを UI へ渡す直前（エラー整形関数の出口）に 1 か所だけ入れる。
入口ごとに入れると、必ずどこかで漏れる。

## 1.4 記録: ログ・標準出力

`print()` と `logging` を全部見る。Streamlit の `print()` は起動したターミナルに出る。
共有マシンや、ターミナルのログを保存している環境では、これが記録として残る。

- キーそのものの出力（`print(f"key={api_key}")`）→ **高**
- プロンプト全文・生成結果の出力 → 内容次第。ユーザーが貼り付けた社内文書が
  ターミナル履歴に残るなら **中**
- 例外のスタックトレースをそのままログに流す → 1.3 と同じ理由で **中**

## 1.5 保存: ファイルとリポジトリ

- `.gitignore` が `.env` を確実に覆っているか。`*.env` と `.env` は挙動が違うので、
  実際のファイル名で確認する
- **git 管理下なら、過去に commit されていないかを確認する。**
  `.gitignore` に追加しても、既に追跡済みのファイルは追跡され続ける

  ```bash
  git ls-files | grep -i -E '(^|/)\.env|secrets\.toml'
  git log --oneline --all -- .env
  ```

  過去のコミットに入っていたら、`.gitignore` を直すだけでは不十分（履歴に残る）。
  キーの再発行が必要だと明記する → **高**
- `.env` のパーミッション。`644` なら同じマシンの他ユーザーが読める。`600` を推奨
- `.env.example` のようなテンプレートに、本物のキーが書かれていないか
- テンプレートのプレースホルダ文言（`ここにAPIキーを貼り付け` など）を「設定済み」と
  誤認しない仕組みがあるか。誤認すると、ユーザーは設定済みだと思ったままダミーキーで
  API を叩き、エラー経由で余計な情報を目にすることになる。この仕組みがあるなら
  「確認したが問題なかった点」に書く
- 生成結果や入力を、ダウンロード以外の経路でディスクに書いていないか。
  書いているなら、保存先ディレクトリが `.gitignore` に入っているかまで見る
