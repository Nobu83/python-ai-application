# Streamlit × LLM アプリのセキュリティ点検

この種のアプリは「自分のマシンで動かす個人用ツール」として作られることが多い。
そのため Web アプリの定番対策（認証・DB のアクセス制御・入力のエスケープ）はそもそも
対象外になりやすく、代わりにこの構成に特有の危険が集中する。

- **API キーが手元にある**。アプリを開ける人は、そのキーの持ち主の課金で API を使える
- **ブラウザで待ち受けている**。ローカル専用のつもりでも、既定では同じネットワークの他人に届く
- **外部から持ってきた文章をプロンプトに入れる**。要約・返信作成などは、まさに他人が書いた
  テキストをモデルに読ませる機能

この 3 つが、以下の 3 観点に対応する。点検はこの順で行う。

| 観点 | 詳細 |
|---|---|
| 秘密情報の漏えい | `references/secrets.md` |
| 公開範囲・起動設定 | `references/exposure.md` |
| LLM 固有のリスク | `references/llm-risks.md` |

各観点に入る直前にそのファイルを読む。最初にまとめて読む必要はない。

## 進め方

### 1. 前提（脅威モデル）を先に固定する

**ここを飛ばすと、レポート全体が的外れになる。**
「認証がない」「データベースにアクセス制御がない」は、ローカル個人用ツールでは
欠陥ではなく設計判断である。前提を決めずに点検すると、直す必要のないものを
「重大な脆弱性」として並べたレポートができあがり、本当に危ない 1 件が埋もれる。

まず `README.md` / `CLAUDE.md` / `docs/` を読み、次を 1 段落で言語化する。

- 誰が使う想定か（自分だけ / チーム / 不特定多数）
- どこで動く想定か（ローカルのみ / LAN / インターネット公開）
- 意図的に持たないもの（DB・認証・永続化など、設計上そう決めているもの）

**プロジェクトが意図的に持たないと宣言しているものを「追加しろ」と指摘してはいけない。**
代わりに「その前提のままリスクを下げる方法」を出す。
例: 認証を足すのではなく、待ち受けアドレスを `127.0.0.1` に絞る。

そのうえで、想定する攻撃者を具体的に挙げる。この構成なら通常は次の 4 者になる。

1. 同じ Wi-Fi / LAN にいる他人（カフェ・コワーキング・社内ネットワーク）
2. アプリに貼り付けられる文章を書いた人（＝プロンプトインジェクションの出し手）
3. 同じマシンの別ユーザー、またはマシンを一時的に触れる人
4. リポジトリや共有フォルダを覗ける人

前提が資料から読み取れないときは、推測で埋めずユーザーに 1 問だけ聞く。

### 2. 事実を集める

推測で書かないために、まず機械的に集められる情報を集める。

```bash
python3 <skill-dir>/scripts/collect_context.py <プロジェクトのパス>
```

このスクリプトは、設定ファイルの有無と権限、`.gitignore` の網羅、外部入力の入口、
危険なパターンの該当行（`file:line` 付き）を一覧にする。
API キーらしき文字列は自動で伏せ字にして出力するので、そのまま画面に出してよい。

出力は**あくまで当たりをつけるための材料**であって、指摘そのものではない。

### 3. 3 観点で点検する

`references/` の各ファイルを順に読み、そこに書かれた観点でコードと設定を確認する。
スクリプトが拾えるのは表層のパターンだけなので、該当ファイルは自分の目で読む。

### 4. 指摘を裏取りする

**grep で当たった行を、そのまま指摘にしてはいけない。** 必ず該当箇所を読み、
「この条件が揃うと、こうなる」と自分で言えるところまで確認する。確認手段の例:

- 疑わしい関数を単体で実行して、実際の出力を見る
  （例: エラーメッセージの整形関数に、キーを含む文字列を渡して何が返るか）
- 起動中のプロセスがどのアドレスで待ち受けているか実際に確認する
- 設定ファイルの既定値は記憶に頼らず、インストール済みのパッケージか公式ドキュメントで確認する

裏が取れなかったものは、落とすか「**未確認**」と明記する。
確度の低い指摘を混ぜると、レポート全体が信用されなくなり、結局どれも直されない。

### 5. レポートを書く

保存先は、`docs/` があれば `docs/security-report-<YYYY-MM-DD>.md`、
なければプロジェクト直下の `security-report-<YYYY-MM-DD>.md`。
日付は `date +%F` で取る（推測しない）。

**このスキルではアプリのファイルを編集しない。** 作るのはレポートだけで、
修正案はレポート内のコードブロックとして示す。適用するかどうかはユーザーが決める。
直してほしいと言われたら、そこで初めて編集に入る。

書き終えたら、会話の中では「深刻度・高の件数と、その中身」「レポートのパス」だけを短く伝える。
レポートの内容を会話に貼り直さない。

## 深刻度の付け方

| 深刻度 | 意味 |
|---|---|
| **高** | 放置すると、金銭的損害か秘密の流出が直接起きる。API キーの流出、第三者による無断利用、任意コードの実行 |
| **中** | 条件が揃えば高に至る。または誤操作で情報が漏れる。今すぐではないが、共有・公開の前には必ず直す必要がある |
| **低** | 実害は小さいが直す価値がある。運用上の注意もここに入れる |

深刻度は、**そのアプリの前提のもとで実際に起きうるか**で決める。
一般論として重大な問題でも、このアプリの構成では成立しないなら低にするか、
「成立しないが、○○を追加した時点で高になる」と条件つきで書く。
逆に、教科書的には軽い問題でも、キーの流出に直結するならためらわず高にする。

## レポートの形式

```markdown
# セキュリティレポート — <アプリ名>

- 点検日: <YYYY-MM-DD>
- 対象: <パスと、見たファイルの範囲>
- 点検した観点: 秘密情報の漏えい / 公開範囲・起動設定 / LLM 固有のリスク

## 前提（この点検が想定していること）

<誰がどこで使う想定か。意図的に持たない機能。想定する攻撃者を箇条書きで。>

## 要約

<3 行以内。高が何件、まず何をすべきか。>

## 指摘事項

### [高] <一文で問題を言い切るタイトル>

**何が起きるか**: <攻撃者が誰で、何をすると、どうなるか。抽象論ではなく具体的な筋書きで。>

**根拠**: `path/to/file.py:42`

<該当コードの引用（数行）>

**修正案**:

<コードブロック。差し替え後の形が分かるように。>

**補足**: <副作用、他に必要な変更、直さない選択もあり得るならその条件。>

### [中] ...

## 確認したが、問題なかった点

<見たうえで問題なしと判断したものを挙げる。何を見ていないかが分かるようにするため、
これは省略しない。>

## 今回の点検範囲外

<例: 依存パッケージの既知脆弱性スキャン、実際に動作させての侵入テスト。
「見ていない」ことを明示する。>
```

指摘が 1 件もなかった場合も、この形でレポートを作る。「確認したが問題なかった点」が
本文になる。**問題を見つけるために無理やり指摘を作らない。**

## このスキル自身が守ること

点検の過程で、API キーや `.env` の中身といった秘密情報を実際に目にすることがある。

- **レポートにも会話にも、秘密情報の値そのものを書かない。**
  「`.env` の 1 行目に有効なキーが平文で入っている」とは書いてよいが、値は書かない
- `.env` や認証情報ファイルは、**存在・権限・`.gitignore` の状況を確認するだけ**にとどめ、
  中身を読む必要がある場合は理由を述べてユーザーに確認する
- 見つけた問題を検証するために、実際に攻撃を成立させる操作（外部への送信、他マシンからの
  アクセス試行など）を行わない。コードと設定を読んで判断する
